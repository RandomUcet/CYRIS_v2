# CYRIS v2.4.6 — Medical handoff acknowledgement and safe status transitions

## Receive handoff, then resume care
- The authorized receiving medical team can explicitly **Receive Patient** after an exercise casualty is transferred to its team. A dedicated event-scoped `POST /events/:eventId/medical/:encounterId/receive` endpoint requires both `medical.intervene` and `medical.read` on that specific patient record.
- Reception uses an encounter row lock and one database transaction for the `TRANSFERRED → UNDER_CARE` status change, immutable audit, operational activity and search outbox. Duplicate acknowledgement or stale record states return HTTP 409, not a second transition.
- Medical number, original transfer timestamp, location, receiving-unit ownership and prior disposition are **preserved**. Reception appends to the same encounter timeline; it does not create a new patient record.
- Original-team accounts cannot use the receipt endpoint after ownership moves because patient resource authorization is reevaluated.
- The web medical detail page exposes **Receive Patient** only when the encounter is transferred and the operator has intervention privileges. Status-aware action controls hide stabilization, triage, transfer and close while handoff awaits acknowledgement or after final closure.

## Status safety
- Transferred and finalized patients cannot be triaged or given a new intervention without receiving the handoff; transferred patients cannot be immediately transferred again without an intermediate receipt.
- Stabilization now accepts only RECEIVED, TRIAGED and UNDER_CARE; closing rejects TRANSFERRED, CLOSED or DECEASED. Both use conditional updates so a concurrent status change is rejected rather than overwritten.
- Normal medical actions no longer silently turn a CLOSED/DECEASED record back into a different status.

## Exercise access and preview accounts
- A dedicated `medical-responder` event-role template now provides the full clinical workflow with **UNIT-scoped** permissions; organizers can assign it to the correct medical team without granting access to every medical record across the exercise.
- A **newly provisioned** CzechCybertron preview medical account receives this role bound to its own medical unit, replacing the old event-wide read/create/observe-only preview profile. Its team can receive, triage, treat, hand off and close fictional patients.
- Existing preview exercises and manually customized role grants remain untouched on re-bootstrap. An organizer must assign the new medical-responder role explicitly to operators in those existing exercises; the template installer adds the missing role but never silently grants it.

## Verification
- Real isolated PostgreSQL regressions: transfer source/receiver authorization; failure-rollback of a handoff receipt; persisted historical transfer timestamp and disposition; duplicate acknowledgement; same-record continued intervention; no reactivation after closing.
- Medical controller scope tests check that the receive endpoint validates event/encounter matching before any clinical operation.
- A web source regression checks the display and endpoint wiring.
- Existing Docker, Redis, PostgreSQL, search, audit and backup infrastructure unchanged; no database migration or destructive cleanup.
- After automated CI, a real two-team browser acceptance test is recommended before live exercise deployment.
