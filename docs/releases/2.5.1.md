# CYRIS 2.5.1 — operational hardening (development)

Branch begins from released-scope 2.5.0 main commit 5fb7068. Release workflow for 2.5.0 is running independently. Focus: exercise time consistency, licence registry usability, access boundaries, regression fixes and operator feedback. Do not publish until validated.

Licence status now derives from the exercise clock and event timezone, with date-only inclusive validity and a separate administrative status. Invalid timezone is unknown rather than host-clock fallback. Manual what-if remains. Registry list identity scope includes user, preview and capabilities. Contract tests cover timezone midnight boundaries. CI pending.

Audit now resolves current account names for actors and user targets in paginated queries, including literal name search before pagination. UUIDs remain in a technical inspector, not primary columns. Timestamp no longer repeats the date. No immutable event or archived payload is modified; names are current, not historic snapshots.

Intelligence Center split into four task-oriented work areas, preserving mounted form and job polling state. The navigation includes local module filtering (authorized routes only) and full label tooltips, while preserving branding. Technical AI IDs move out of everyday views. Browser acceptance pending.

Licence holder/issuer selection now uses the permission-filtered registry picker with server-side entity type filtering before the result limit. No bulk person/organisation dropdown, no UUID copying. Creation checks distinct selected records and fences asynchronous form responses against identity/tab changes.

First diagnostics increment: `sudo cyrisctl diagnostics --summary --minutes 60` produces JSON containing bounded per-service fixed-category log counts only. No raw logs, excerpts, host details, credentials, identifiers or model calls. Unavailable service sampling is explicit. Counts are matching log lines, not distinct incidents. This is a safe transport input for subsequent local Spark diagnosis; not yet Spark inference or an automated monitor.

Spark diagnostics stage 2: platform-managed endpoint and System Health panel accept only a strict fixed-category CLI summary, use the managed Spark gateway and regular shared admission with an exclusive diagnostic scope, validate every finding against positive observed counts, and allow copying a structured report. No raw logs or autonomous changes. CLI-to-API direct authenticated transport and scheduled notifications remain follow-up. Contract tests cover injection-shaped inputs and unsupported findings.
